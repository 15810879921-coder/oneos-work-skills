# OneOS 独立工作体系

面向产品经理转向 FDE 的完整工作流技能集：从需求、业务规则和体验设计，到代码实现、测试分支交接，再到测试人员部署后的验证与缺陷复测。四个入口可以按需使用，也可以连续接力。

此仓库为公开完整版，包含版本化的 OneOS 设计规范快照；业务/开发知识正本仍在原云端仓库，访问需要各自授权。包内不含访问凭据。

本套独立维护，不依赖团队 FDE skill，也不会自动替换它。它把工作方法、交接材料、工具和证据规则一起交给 AI；实际执行仍需要模型、项目代码、平台工具和相应权限。

## 当前版本：v1.1.1

- 查询优化不预设批量优于逐条。先核业务语义和权限，再用可比的端到端耗时与资源成本选择方案；无收益证据时允许保留现状。
- 非空校验结合需求及对应开发任务，区分必填/可空、未传、null、空串、空集合和0，不统一强制非空或自动填默认值。
- 开发、验证、知识来源及专项回归同步更新；规则回归通过不代表真实业务或性能验收通过。

## 一键安装 / 更新

前提：本机可以运行 Node.js / npx。下面安装到当前用户的 Codex 全局技能目录；重复执行可更新这四个入口，不更新其他团队 skill。

```bash
npx skills add 15810879921-coder/oneos-work-skills --skill '*' -a codex -g -y
```

只安装需要的能力，把 `'*'` 换成对应名称：

```bash
npx skills add 15810879921-coder/oneos-work-skills --skill oneos-work-delivery -a codex -g -y
npx skills add 15810879921-coder/oneos-work-skills --skill oneos-work-verify -a codex -g -y
npx skills add 15810879921-coder/oneos-work-skills --skill oneos-work-knowledge -a codex -g -y
npx skills add 15810879921-coder/oneos-work-skills --skill oneos-work-ux -a codex -g -y
```

使用其他兼容客户端时按其支持的 Agent 标识替换 `codex`。安装后开启新会话，指定使用新入口；不要把两套相互冲突的工作流同时用于同一任务。

HiFox：上面的命令是 Codex 安装方式，不等同于导入 HiFox 云端技能。[Release](https://github.com/15810879921-coder/oneos-work-skills/releases) 提供四个独立 ZIP；按客户端实际支持的导入方式保留完整目录。HiFox CLI 目前显示支持 clawhub.ai / skills.sh 来源 URL，本仓库不把未经验证的 skills.sh 页面当成可用安装链接，也没有代用户创建平台技能。

安装工具与参数依据：[skills 官方安装文档](https://github.com/vercel-labs/skills/blob/main/docs/commands.md)。

## 四个入口，分别解决什么

| 入口 | 适合谁 / 什么时候 | 主要交付 |
|---|---|---|
| `oneos-work-delivery` 独立交付 | 产品、FDE、开发：从诉求推进到可提测代码 | 需求和验收点、实现、自检、合入证据、测试交接 |
| `oneos-work-verify` 独立验证 | 测试、FDE：测试环境部署完成后 | 版本核验、风险用例、真实测试结果、缺陷和复测证据 |
| `oneos-work-knowledge` 双库知识 | 所有需要查规则、查实现、沉淀经验的人 | 双库关联、固定版本来源、冲突和缺口、可审阅净变化 |
| `oneos-work-ux` 体验规范 | 产品、设计、前端、测试：界面设计和验收 | 适用标准、组件和交互要求、体验评审、规范例外 |

### 1. 产品到开发：把想法变成可验收的实现

- 从碎片诉求整理目标、范围、非目标、角色、状态和字段，补齐正常、异常和权限路径，并给验收点编号。
- 先查业务依据，再核实际源码；区分业务规则、技术现状和待确认信息，避免用旧页面反推业务。
- 小优化使用简短验收卡；跨模块变更按需形成产品/技术方案、接口和数据变化、兼容性及关联回归范围。
- 读取仓库约束和必读工程资产；检查已有改动、隔离工作区，结合已有组件实现与自检，保留真实检查证据。
- 核测试分支保护规则、提交范围和触发器；在授权范围合入并读回验证，交接页面入口、角色、数据、依赖和缺口。
- 默认止于“等待测试人员统一部署”。如果合分支会自动部署或触发行为不明，停在安全工作分支/MR，不擅自改流水线。

### 2. 测试和返修：有版本、有断言、有证据

- 测试人员部署后，先核实际前端、后端和依赖组件的构建/提交版本。版本不匹配的范围不会被算成已验收。
- 从验收点生成 Given/When/Then 用例，按风险覆盖正常、边界、异常、权限、空态和关联影响。
- Playwright 负责稳定操作及确定性断言；Midscene 辅助视觉定位、操作和观察。金额、数量、状态、接口结果、导出文件等必须有可核验预期。
- 包含可运行的 Midscene + Playwright 模板、模型/环境前置检查，以及合成筛选和 CSV 导出冒烟案例；需接入真实项目再形成业务用例。
- 区分产品缺陷、环境问题、AI 定位失败和模型超时；保留首轮失败、证据和有限重试记录。
- 每条验收点记录 passed / failed / blocked / not_run；未测和跳过不算通过。修复后回测试分支，等待下一次统一部署，再复测原失败和关联范围。
- 同一实施者自验如实标记为自检或辅助验证；不会仅凭“独立验证”这个名称伪装成独立 QA。

### 3. 双库知识：业务和开发打通，并控制上下文开销

- 业务规则与开发实现以可追溯关联连接，保留原有两库分工；查到规则可以继续定位实现，发现实现差异可回查业务依据。
- 固定来源提交、文件和哈希，保留 confirmed / frozen / pending 等状态；父级确认不会自动把关联草案变成正式规则。
- 明确区分“找到位置”“核过正文”“实际运行验证”，不把历史索引当成当前运行证据。
- 先读轻量索引，再由程序筛选命中条目，默认最多 5 条，按任务加载相关完整规则；必读项和例外不因节流被省略。
- 默认本地知识缓存上限 32 MiB，按版本复用；知识正本留在云端，不自动克隆整库，也不把整库塞进上下文。具体 token 收益需要实测。
- 沉淀只处理可追溯的净变化，查重后通过授权工具同步；双库部分成功会保留状态，不虚报全部入库。

### 4. 体验规范：设计标准贯穿交付与验证

- 继续拥有设计标准、页面模式和体验评审职责，明确适用的规范版本、页面类型、组件和交互规则。
- 在方案阶段确定规则，实施阶段检查组件/Token/状态，验证阶段检查实际截图、布局和交互。
- 按任务检查表格、表单、弹层、滚动、空/错/加载/权限状态、反馈、主题、宽窄屏、键盘可达与可读性。
- 不凭个人审美覆盖规范，不用静态类名匹配代替真实视觉验收，也不把失败截图自动更新成通过基准。
- 规范例外记录原因、范围、决定来源和复核条件；业务规则、体验表达与工程约束冲突时给出可比较方案。

## 可以直接这样说

> 用 oneos-work-delivery 处理这个需求，先查业务和开发约束，实现并自检后进入测试分支，等待统一部署。

> 测试环境已经更新，用 oneos-work-verify 核验实际版本，再测试这次交付，输出缺陷和证据。

> 用 oneos-work-knowledge 查这条业务规则，找对应实现，列出来源版本和证据缺口。

> 用 oneos-work-ux 评审这个页面，检查布局、组件、空错载权和交互反馈，并给出可实施的整改项。

## 接入、边界和验证

首次接入需要真实仓库、目标分支、任务平台、测试环境、账号角色、数据约定和正式规范来源。优先由 Agent 查询已授权信息，只补问缺口。密钥用安全环境配置，不写进 skill 或知识库。

v1.0.0 已完成 Python 边界测试、技能包完整性检查、Midscene 模板类型检查、真实浏览器中的合成冒烟，以及 GitHub 远端四包安装和安装后完整性校验，历史记录保留在原验证报告。v1.1.1 按变化范围完成包结构、17条保真、加载边界及定向规则场景复核；未将旧版浏览器或安装测试冒充新版重跑结果。真实模型推理与 OneOS 业务验收需在授权环境接通后执行。

不负责生产发布，也不抢测试人员统一部署；没有事件执行器时不承诺会话结束后自动醒来。详见 [完整导入说明](docs/导入与使用说明.md) 与 [验证报告](docs/验证报告.md)。

## 维护与构建

在 `source/shared` 维护公共内容、`source/entries` 维护入口，执行以下命令生成 `skills/` 四个独立安装目录和 `dist/` 四个独立ZIP：

```bash
python3 build.py
python3 tests/test_packages.py
```

构建自动更新各包的文件SHA256及sharedDigest。`dist/` 不入Git，作为Release附件交付；`skills/` 提交到仓库供安装器发现。不要只改生成目录而遗漏维护源。
