# Java 后端技术子规则

版本 1.1.1。由 [主体规则](java-backend-rules.md) 的触发索引加载适用章节；命中则必须满足。机制本身不是验收结论，引用文档也不是目标项目已具备能力的证据。

## 中文行注释

适用：新增或修改的 Java 代码及对应 Java 测试、示例。每个非空代码物理行都有对应中文行注释，包括 package/import、注解、链式续行和独立大括号；解释意图、约束或边界，不复述无意义语法。仅新增/修改行受此约束，不为补注释重写未修改历史代码，不写凭据或敏感信息。

语法/内容保护例外：字符串、SQL、文本块内容行不能插入会改变实际数据的注释。对这些内容保持字节语义，在合法位置逐行对应说明并记录例外；Javadoc、已有注释和空行不机械追加行尾注释。不得通过拆碎表达式、改 SQL 或创建无意义变量凑注释覆盖。检查编译及相关文本/SQL行为，不能仅以正则存在中文判定语义正确。

<a id="null-semantics"></a>
## 空值、查询边界与需求任务联动

适用：查询入参、返回字段、对象映射、局部更新或数据库空值设计。是否校验非空、允许为空以及空时如何处理，由需求、关联开发任务及现有接口契约共同决定；不能统一添加 NotNull/NotBlank、提前返回、默认值或 SQL IS NOT NULL。判空防异常与业务拒绝空值是两件事。

- 对本次受影响字段，记录需求/任务来源、使用场景、是否必填、未传/null/空字符串/空集合/0的语义、校验与查询或更新行为、验收例子；已有清晰契约可引用，不强制全系统逐字段建表。需求摘要保持易读，开发任务补足可执行细节；代码现状不是自动裁决依据。规则冲突或关键语义缺失时标出待确认项，只暂停依赖该决定的实现。
- 详情ID、必需租户/权限上下文、限定对象的必填查询条件缺失时，按契约拒绝或安全失败，不能因跳过条件意外变成全量/越权查询。可选筛选条件为空则按约定不筛选、匹配空值或报错，不机械拒绝；允许无筛选的列表仍保留权限、分页和查询边界。
- 空集合究竟表示“不筛选”“匹配零条”还是非法输入须明确，不能让 IN 空集合的构造行为决定业务。需要匹配数据库 NULL 时使用正确空值语义；不能随意增加 IS NOT NULL 或将 LEFT JOIN 改成 INNER JOIN，导致合法缺失关联记录被丢弃。
- 返回无关联、未维护、尚未发生等合法空值应保留语义并安全映射；不能为消除空值填0、空对象、当前日期或当前客户。零金额/零里程不等于缺值；接口失败、无权限与成功但无记录也不能混为一谈。
- 局部更新明确“未传不改”“显式null清空或拒绝”“空字符串/集合如何处理”；普通实体复制或统一非空更新不能代替字段契约。涉及金额、历史归属、状态或时间边界时保持相关业务约束。
- 验证必填缺失、合法空值、可选条件为空、0值、空集合、无关联及权限路径。只有实际涉及局部更新时才增加未传/置空用例；不为了补判空扩展无关改动。

## 并发、JDK 与资源预算

先从构建、运行配置核 JDK、框架、驱动和部署版本；先定位 N+1、重复读取、差 SQL 是否造成实际瓶颈，不能仅因逐条调用就预设批量化。按[查询方案选型](#query-selection)比较可行方案。只有独立 I/O 位于关键路径、客户端可并发、无需同一事务快照且下游容量有余量时，才评估并行收益。单查询、依赖查询、CPU轻量计算或无收益证据时可以保持同步；批量/合并查询也是合法选择。不以“数据库支持并发”推出“必须异步”。

- Java 8：CompletableFuture 使用显式有界平台线程执行器；不能使用 Java 9 才加入的 orTimeout/completeOnTimeout。采用客户端/驱动超时和有界等待或项目已有超时编排。
- Java 17：可用上述超时 API，但超时完成不代表底层调用停止。阻塞 I/O 仍用显式受控执行器，不用 commonPool 或 parallelStream 承担请求阻塞查询。
- Java 21+：阻塞 I/O 可考虑每任务一个虚拟线程；不池化虚拟线程，用独立准入/信号量等限制下游并发、等待量和扇出。虚拟线程不增加数据库容量，也不是 CPU 运算提速手段。按实际 JDK 检查阻塞/钉住行为，不能把 Java 21 的限制泛化到所有后续版本。
- CPU密集任务按CPU预算限制并行；只有现有端到端非阻塞栈支持时才考虑响应式方案，不为单接口强加整套框架。

平台线程数、队列、请求扇出、并发请求和连接需求必须形成同一预算，计入其他接口、后台任务和集群实例。避免父任务持有连接、等待需要同池连接的子任务导致耗尽/死锁；优先缩小持有范围、同步/批量或经验证的资源隔离，不能只扩大线程池。

用同一截止时间分配排队、获取连接、连接、读取/SQL和汇聚预算；层层重试不能重新获得完整预算。Future 超时/cancel 不保证 SQL 停止，需核驱动取消能力与服务端超时，保证最终连接释放并观察遗留任务。明确全成功或部分降级，失败不能伪装完整空结果。显式传递最小身份、租户和追踪上下文，线程复用时恢复/清理；不跨线程共享 Connection、Session 或父事务资源。

<a id="transactions"></a>
## 事务、快照与提交未知

按实际调用路径、事务管理器、代理/自调用、异常类型与隔离级别验证事务真正生效。不统一强加 public 或 rollbackFor；不能只数注解。跨线程独立事务、readOnly=true 都不证明同一快照。

要求同一快照时，核具体数据库、隔离级别及普通一致性读/锁定读类型。例如 MySQL InnoDB 的 REPEATABLE READ 一致性读与 READ COMMITTED 每次读取的新快照不同；即使同一事务也不能混淆锁定读与快照读。选择能满足业务的一致性查询方案，通常保持同一事务内顺序读取；独立并发事务不能自行承诺同一快照。

提交响应丢失/超时应区分明确失败与结果未知。按业务唯一标识、幂等记录或权威状态核实结果，再决定重试/补偿；不能直接重复扣款、扣库存或发送外部副作用。测试必须包含提交前失败、提交成功但响应丢失等边界。

<a id="idempotency"></a>
## 并发写与幂等原子性

并发控制与幂等是不同问题。原子条件更新、版本号、唯一约束和行锁按竞争风险选择并核影响行数；乐观锁不能代替重复请求识别。

需要幂等时定义键作用域（租户/业务动作/业务标识）、请求指纹、状态和有效期。同键同请求按处理中/成功/失败的约定返回；同键不同业务载荷必须拒绝，不能返回上次成功。唯一约束或等价原子占用防并发“先查再写”。幂等记录与业务变更要有原子保障：同一本地数据库优先同事务；跨资源需明确可恢复协议和故障窗口，不能靠 Redis 占位加独立数据库写入声称原子。

消费去重记录与本地业务效果也需原子提交；外部副作用用下游幂等标识、结果核实与必要补偿。验证同时重复请求、处理中重入、崩溃恢复、同键异载荷及业务提交后响应丢失；不得承诺未经证明的跨服务 exactly-once。

<a id="reliable-async"></a>
## 可靠异步与真实状态

只有业务允许稍后完成时采用异步业务任务。需要可靠受理时，必须有持久化且可恢复的任务意图，再返回“已受理/处理中”以及实际可用的查询/失败反馈方式。受理不等于完成；不需要可靠投递的可丢弃工作也要明确其业务容忍依据。

提交后回调/AFTER_COMMIT 仅限定执行时机，不能消除“业务已提交、进程在发布前崩溃”的窗口。数据库变更触发可靠消息时，优先复用项目已有保障；可用业务写入与 Outbox 同一本地事务、持久化中继重试及确认进度、幂等消费，或能证明同等保障的既有 CDC/事务消息机制。单独落库后即忘、内存线程池排队或只注册回调不算可靠受理。

按需求处理重试退避、并发领取、顺序、失败/死信和补偿；恢复时允许重复投递，但不能重复业务效果。验证事务回滚无消息、提交后发布前崩溃、发布后确认前崩溃、重复消费、下游长期失败。持久化只是手段，恢复证据才说明该故障路径满足要求。

<a id="consistency"></a>
## 缓存、权限与写后读

缓存和读写分离分别评估收益、新鲜度和一致性；单实例/跨实例按实际架构选择，不默认引入 Redis 或多级缓存。容量、TTL、加载并发、失效和故障路径均有边界；异常和越权不得缓存成“不存在”，空结果仅在业务允许时短期缓存。

Key 覆盖租户、权限/用户范围、查询参数及所有影响结果的因素；共享公共数据有明确依据才可省略用户维度。缓存命中也必须完成当前请求鉴权及数据权限校验；权限版本/失效方案要覆盖撤权时效，不能以旧 key 或 TTL 掩盖撤权后越权访问。跨实例、权限变更、穿透/击穿及上下文清理均按实际影响验证。

先确定写后读需要覆盖的后续请求、会话或业务窗口，不只当前方法。关键写后读、库存/余额决策默认走主库；已核验复制进度的方案可以采用，但不能仅凭“延迟通常很小”使用副本。主库路由不自动解决旧事务快照、缓存或整个业务约束。

写入与失效失败、并发旧值回填、跨实例延迟都要检查。主动失效、延迟双删、版本 key 或 TTL 单独都不能证明强一致；版本方案需验证版本来源和读取/写回的原子性。不能接受旧值时绕过缓存并读取满足该业务一致性语义的权威数据源；验证写后立即读、后续请求、撤权、多实例和旧值晚回填。

<a id="database"></a>
## SQL、索引、迁移与软删除验证

查询形态的选择先执行下节；索引与查询次数均不能单独证明性能收益。

值参数绑定，动态标识符由固定分支/服务端白名单映射；不能直接拼接客户端字段。索引按实际 SQL、已有索引、执行计划、代表性数据量/倾斜及读写成本选择；还要验证实际延迟、吞吐及写入维护代价。执行计划改变不等于收益成立，允许“不新增索引”的结论。删除冗余索引前核其唯一性/约束作用和其他查询依赖。

迁移需核当前真实结构、历史兼容及回填/大表 DDL 影响；版本化脚本不证明实际已执行或结构正确。本套仍不直接写共享 TEST/PROD 数据库，验证环境和数据操作遵守既有授权。

软删除唯一性覆盖有效记录、历史多次删除、重建、恢复及并发。布尔 del_flag 与业务键组成唯一索引不天然容纳多份历史；按数据库能力与生命周期选择有效行唯一性或等价设计，不能统一强加软删除。

<a id="query-selection"></a>
## 查询方案选型：先核语义，再比较成本

适用：提出查询性能建议、发现逐行/N+1/重复查询、调整批量/合并/并发方式。单条、逐条索引查询、批量、合并和受控并发都是候选，经过语义及资源准入后没有固定优先级。“查询次数多”“循环内查库”“SQL更少”只是排查线索，不能直接推出必须批量、合并或异步。

1. **先固定业务语义与目标。** 核部署版本、调用链、SQL、真实结构/索引和性能目标；明确结果、权限/租户、有效与历史关系、时间边界、分页/排序/总数、金额及快照要求。方案改变这些语义时先解决需求缺口，不能以提速替代业务裁决。只读分析不获得改业务代码、写库或压测共享环境的授权。
2. **保留现状基线，按瓶颈选候选。** 分辨数据库执行、网络往返、远程调用、传输和组装的成本。批量候选限定本页/本批对象及所需历史范围，不为少查几次加载全部历史；逐条索引查询也可能更快、更省资源。无需穷举所有机制或为已有低延迟实现强行实验。
3. **比较可比的端到端结果。** 在结果一致、同权限、同数据/参数、同版本及可比负载下，按风险覆盖代表性页大小、关联基数/历史密度、数据倾斜及相关缓存状态。计入整个调用链耗时、扫描/排序、传输、内存与连接占用；按目标补充重复采样、P95/P99、吞吐和错误率。不得把孤立单条 SQL 时间与批量完整接口时间混比，不能把一次 EXPLAIN 或一次偶然样本当收益证明。
4. **按证据选择并允许不改。** 逐条方案更合理就保留逐条；批量明确获益且语义/资源满足要求才采用。不同规模出现交叉时，优先选择最简单且满足目标的方案；只有收益足以覆盖复杂度时才引入分段策略，阈值来自测量，不能固定拍脑袋数值。语义不正确的快方案不可选。
5. **无测量证据时只给条件方案。** 输出已知事实、业务待确认项、基线/候选、验证方法及采用/保留条件；不得把“待比较的批量方案”写成“确定改为批量”，不得承诺更快或最优。说明未实测，继续完成不依赖该结论的只读分析。普通小改动不因此强制全仓压测。

示例：历史归属查询应比较“本页逐条按车辆与发生时间索引查找”和“限定本页及时间范围的批量匹配”，先验证交还车边界与客户结果一致，再判断端到端收益；不能用当前客户代替历史匹配来制造提速。

<a id="verification"></a>
## 定向验证与证据

以改动、调用链和风险选相关编译、单元/接口/行为测试，覆盖适用的正常、异常、边界和权限路径。历史证据仅在代码/依赖/配置/环境/数据条件仍适用且可追溯时复用；改变后重验受影响部分。普通改动不强制全仓测试或压测。

声称优化带来性能收益时，在可比数据与负载下对比基线，观察适用的吞吐、P95/P99、错误率、CPU/GC、连接池及下游压力；没有环境或预算就明确未实测，不能宣称“最优”。验证失败先定位并最小修复，不覆盖他人工作。Skill八组场景回归只证明规则的指引效果，不代替真实Java执行、数据库故障注入或业务验收。
